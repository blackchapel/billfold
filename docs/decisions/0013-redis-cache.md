# 0013 Shared cache (Upstash Redis)

**Context.** After the speed pass (ADR 0012) pages still read lists and reports from the database on every view, and every filed item asked Google for a fresh access token and looked up each folder level again. A shared cache removes that work, but a cache that serves old data is worse than none, so the design is about invalidation first.

**Decisions.**
- **Optional and disposable.** `Cache` is a port (`domain/ports/cache.ts`). Upstash Redis over HTTPS (`UpstashCache`, free tier, Mumbai) is used when `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` are set; otherwise `NoopCache` makes every read a miss and the app behaves as it did before. Test mode uses an in-process `MemoryCache` with identical behaviour, so the end-to-end flows exercise the real invalidation code. Every call is cut off after 150 ms; three failures in a row switch the cache off for 30 seconds; errors are never thrown. Redis being slow or down can cost at most one slow request.
- **Versions, not deletes.** Each organisation has a version per kind of data (`CACHE_TAGS`: members, connections, sources, runConfigs, recipients, templates, bills, sends, runs). A cached screen is stored under a key that contains the versions of everything it was built from (`readThrough`, `queries/cached.ts`). Saving data gives its kind a new version, so old screens are never read again and simply expire. **Lifetimes:** copies of lists and reports and the version tags live 35 days (the app is used about once a month, so a short life would make the cache useless at the next visit; the version, not the TTL, keeps them fresh); Drive folder ids 35 days (forgotten on a Drive 404 and looked up again); the login allowlist answer 10 minutes and the org list 60 seconds (they gate access, so a lost bump must not leave them stale for long); Google access tokens 45 minutes (Google expires them after an hour); OAuth state 10 minutes. Versions are unique tokens (time plus randomness), never counters: a lost or evicted counter cannot restart at 1 and bring an old entry back.
- **Readers are safe against races.** The versions are read before the database is asked, so a slow reader that finishes after a save files its answer under the old versions, where nobody looks. A test reproduces exactly that.
- **Invalidation lives with the data, not with each use case.** Every repository is wrapped (`infra/cache/invalidating.ts`) and a single registry (`infra/cache/specs.ts`) says what each method is: plain, a cached read, or a write and what it bumps. The wrapper bumps after the write returns (so after the commit). A test lists the methods of every real repository class and fails if one is in none of the groups, so a new method cannot be added without deciding what it does to the cache; another test checks that every kind of data is bumped by some write. If bumping fails the data is still saved and old screens expire by themselves.
- **Targeted keys.** The allowlist answer (60 s) is deleted when the allowlist changes, so removing someone still locks them out at once; a person's organisation list and permissions (60 s) are deleted for the person when their role or overrides change or they are removed, and for everyone in the organisation when it is renamed or deleted. Google access tokens (45 min) are stored sealed with the master key under a fingerprint of the refresh token and deleted when the grant is revoked; Drive folder ids (1 h) are forgotten and looked up again when Drive answers 404.
- **Never cached:** secrets or decrypted values (tokens are sealed), run and send progress pages and claims, the audit log, anything per person.
- **Escape hatch.** Settings > Cache > Clear the cache (needs `org.manage`, audited) gives every kind of data a new version and drops the organisation's membership lists.

**Consequences.** Anything that changes the database without going through a repository (a manual edit in the Supabase dashboard, a migration that rewrites data) is not seen by the cache until the cache is cleared in Settings (entries otherwise live 35 days); tests that edit rows directly call the test-only `/api/test/cache` endpoint. If Redis is down while someone saves, other people may see the previous version of a list until that data changes again or the cache is cleared (up to 35 days). The bump failure is logged as `cache_bump_failed`. The free tier allows a monthly number of commands; a page view costs a handful. Cached lists and reports sit in Upstash, so the privacy policy names it as a processor.
